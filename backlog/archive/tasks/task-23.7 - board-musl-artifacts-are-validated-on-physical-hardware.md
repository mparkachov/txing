AC2 prep blocker: on the physical Alpine board, mise 2026.7.12 refused to resolve txing-cyberbrick-*@latest right after publishing cyberbrick-v0.15.5, warning 'no versions found ... matching date filter'. Cause: mise's minimum_release_age setting (default 24h; env MISE_MINIMUM_RELEASE_AGE) is a supply-chain guard that hides releases younger than the window, so a fuzzy 'latest' request resolves to nothing minutes after publish. AC2 real defect found on physical Alpine board and fixed: the musl-dynamic KVS master could not establish TLS to the AWS signaling endpoint on Alpine (X509_V_ERR=20 'unable to get local issuer certificate' at depth=2), so describeChannel/signaling never connected. Root cause: the cyberbrick build points the KVS SDK's TLS at Alpine's full /etc/ssl/certs/ca-certificates.crt (140 certs), but the SDK's TLS layer follows the server-presented chain and needs the single Starfield Services Root CA G2 anchor that AWS chains to; the full bundle fails where a one-cert anchor file succeeds (proven on-box: openssl s_client verifies with the bundle via trusted-first, but the KVS binary does not; extracting just Starfield Services Root CA G2 to a one-cert file and pointing the binary there made signaling connect through GetToken->Describe->GetEndpoint->GetIceConfig->Connect cleanly). This is the same anchor the Debian unit build already uses (its compiled default is the single Starfield G2 file). Fix: (1) kvs_session_real.cpp ResolveSignalingCaCertPath() now honors a runtime TXING_KVS_SYSTEM_CA_CERT_PATH env override (was compile-baked only); (2) runbook provisions /etc/txing/kvs-ca.pem by extracting Starfield Services Root CA G2 from the OS bundle and the KVS OpenRC init script exports TXING_KVS_SYSTEM_CA_CERT_PATH to it; (3) added 'openssl' CLI to runbook step 2; (4) OS/ABI contract documents the single-anchor requirement; (5) test_versioning guards the env override in code + the runbook steps. cyberbrick bumped 0.15.5->0.15.6 for the release carrying the env override. Note: cross-distro smoke passed on 0.15.5 because it only checks linkage/--version, never a live AWS TLS handshake (no creds in CI) - this class of bug is invisible to smoke. Linkage gate itself passed on 0.15.5: static daemon+worker, KVS master resolving libcamera.so.0.7 + full webrtc stack after the full step-2 package install.

CA fix design revised (operator feedback): instead of extracting the anchor into /etc/txing on the board, the Starfield Services Root CA G2 (SFSRootCAG2.pem) is now fetched from AWS's public repository by just aws::cert and shipped in the daemon config bundle alongside AmazonRootCA1.pem, landing in .config/txing/cyberbrick-daemon/ - reusing the existing cert-provisioning mechanism. shared/aws/scripts/aws_lib.sh: txing_cert_create_iot_bundle curls SFSRootCAG2.pem (chmod 644); txing_cert_write_runtime_tarball includes it (shared by rig + device daemon bundles; rigs ignore it, harmless). KVS OpenRC init script points TXING_KVS_SYSTEM_CA_CERT_PATH at /root/.config/txing/cyberbrick-daemon/SFSRootCAG2.pem. Removed the on-board openssl extraction step and the openssl CLI package addition. Note: AmazonRootCA1.pem (already in that dir) was tested and does NOT work - AWS presents Amazon Root CA 1 cross-signed by Starfield G2 and the SDK needs the Starfield issuer, so the new SFSRootCAG2.pem is required, not a reuse of the existing root. Code env override (0.15.6) unchanged. Tests: 143 pass; test_template_policy asserts the SFSRootCAG2 download.

Five defects found, all fresh-install-only and all invisible to CI:

(1) Bridge socket path mismatch - the daemon binds TXING_BOARD_VIDEO_BRIDGE_SOCKET_PATH from daemon.env while the KVS OpenRC init script exports its own path; a unit-generated bundle names /run/txing-unit-daemon/... against cyberbrick services expecting /run/txing-cyberbrick-daemon/... The KVS master then loops forever on GetWorkerConfig and never reaches camera init, so video capability never rises and REDCON pins at 2. The same mismatch hit the hardware worker socket, surfacing as 'connect to hardware worker: context deadline exceeded' with control unusable while video worked. Diagnosis is slow because the daemon logs to CloudWatch (empty local log by design) and the only local symptom is the worker's connect-failure loop.

Design fix (replaces the initial per-board workaround of exporting the paths in OpenRC start_pre, which pinned the runtime paths by hand and reintroduced exactly the per-device coupling that caused the bug): TXING_BOARD_VIDEO_BRIDGE_SOCKET_PATH and TXING_HARDWARE_WORKER_SOCKET_PATH are removed from both the unit and cyberbrick daemon.env.template files. Every binary already compiles device-correct defaults (unit config.go DefaultBoardVideoBridgeSocket/DefaultHardwareSocketPath -> /run/txing-unit-*; cyberbrick equivalents -> /run/txing-cyberbrick-*; hardware_worker config.hpp socket_path) and falls back to them when the env value is empty, so local socket paths now follow the installed binaries rather than the identity bundle. Both env vars remain accepted as overrides for non-standard layouts. This makes the mixed case correct automatically: a unit-generated bundle deployed against cyberbrick binaries resolves cyberbrick socket paths, matching the cyberbrick OpenRC services that create the /run directories. The KVS master keeps its init-script TXING_BOARD_VIDEO_BRIDGE_SOCKET_PATH export by design - its config field is std::optional with no default and its presence is what selects bridge mode over standalone mode (kvs_master config.cpp). test_template_policy now asserts both templates omit the socket paths.

Restart-order finding: restarting the daemon always requires restarting the KVS master afterwards. A daemon restart resets video state to starting and recreates the bridge socket, but the KVS master latches ready_emitted on the first keyframe and never re-reports READY, so it keeps streaming while the daemon believes video never came up - video capability stays false, REDCON falls back to 2, and MCP reports the WebRTC data channel unavailable. ReportVideoState is best-effort and logs nothing on failure, so the failure is silent. Documented as a Restart Order section in the runbook.

(2) camera_auto_detect=1 absent - the runbook enabled only the PWM overlay, so no sensor, unicam, or /dev/video0 ever appeared.

(3) bcm2835-codec not autoloaded - no /dev/video11, the hard-coded V4L2 H.264 encoder path in video_capturer_libcamera.cpp.

(4) libcamera-raspberrypi not installed - the runbook's apk list carried libcamera-dev only, which satisfies the KVS master's link requirements (libcamera.so.0.7, libcamera-base.so.0.7) but omits the rpi pipeline handler, ipa_rpi_vc4.so, and /usr/share/libcamera/ipa/rpi/vc4/ tuning files.

(5) No udev daemon - libcamera links libudev.so.1 and therefore uses its udev device enumerator, not the sysfs fallback. apk satisfies so:libudev.so.1 with eudev-libs (the shared library) alone, so a board with no eudev has no /run/udev and libcamera enumerates zero cameras while /dev/media0 works normally and media-ctl reads it fine. bcm2835-isp also had to be loaded (the vc4 handler needs an ISP media device alongside unicam). setup-udev from alpine-conf was not present on this image; the services were wired manually into sysinit (udev, udev-trigger, udev-settle) - sysinit placement matters so enumeration precedes the txing services and survives the read-only-root reboot.

Defects 2-5 all surface as the identical KVS master error 'configured camera index is not available' (the capturer's index-vs-count check with enumerated count 0), which is why the diagnosis needed LIBCAMERA_LOG_LEVELS=*:DEBUG; 'Unable to acquire a Unicam instance' from rpi/vc4 was the decisive line ('Unable to acquire a CFE instance' from rpi/pisp above it is the Pi 5 handler correctly declining, and is harmless). Root cause of the class: the §2 package list was derived as "the proven runtime superset from the pinned Alpine build container", but a build container needs neither a pipeline handler nor a udev daemon nor kernel modules - anything required only at runtime on real hardware was structurally invisible to that derivation. release/scripts/smoke-board-cross-distro.sh inherits the same blind spot: it provisions that same superset and asserts only --version, so it passes on a board that can never see a camera, exactly as it passed on 0.15.5 with the signaling TLS bug.

Runbook updated (docs/components/cyberbrick-board.md): §2 adds libcamera-raspberrypi + eudev + v4l-utils with an explanation of the runtime-vs-link distinction; new §2a wires udev into sysinit; §6 renamed to "Enable PWM Overlay And Camera" and adds camera_auto_detect=1 plus bcm2835-codec/bcm2835-isp in /etc/modules with post-reboot verification; §8 adds the --camera-probe/TXING_KVS_READY confirmation and the udev-after-reboot check; new Troubleshooting section with a symptom/cause/fix table for camera enumeration and a section on the bridge-socket failure mode; OS And ABI Contract gains a bullet that libcamera linkage is necessary but not sufficient; Release Artifacts documents what the CI gates do and do not prove.

Runbook disk-layout fix (divergence found on hardware): the board's Alpine 3.24 'setup-disk -m sys' produces a UUID-based /etc/fstab with the boot FAT at /boot, NOT the /media/mmcblk0p1 + /dev/mmcblk0pN scheme the runbook assumed (that mount only exists during the diskless boot). The old fstab/aliases would have failed or risked an unbootable board. Fixed cyberbrick-board.md: §1 notes the post-sys-install /boot+UUID layout; §6 PWM overlay targets /boot/config.txt|usercfg.txt with an include check; §7 fstab is UUID-based (/ and /boot -> ro) with root-rw/root-ro aliases using /boot. Confirmed working on hardware (the reboot check above ran on this fixed layout). 143 versioning tests pass.
